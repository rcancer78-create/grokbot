# grokbot: техническое руководство

Это сохранённая техническая справка и история реализации. Команды выполняются из корня репозитория; актуальный старт описан в [README](../README.md). Исторические проверки ниже не означают, что живой сервис повторно проверен при публикации.

Версия 0.3.7. Использует **сессию Grok Bot и его лимит**. Ключи OpenAI/xAI не нужны.
Это адаптер частного протокола, с явно описанной частичной совместимостью OpenAI API.

## Быстрый запуск

Windows, Node.js >= 20.3 для сервера (Node >=22 для SDK-тестов), установленный Grok Bot с выполненным входом:

```powershell
git clone https://github.com/rcancer78-create/grokbot.git
cd grokbot
npm ci
$env:GROKBOT_TOKEN = node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64url'))"
npm start
```

Подключение клиента:

- Base URL: `http://127.0.0.1:8788/v1`
- Model: `grok-bot`
- API key: значение `GROKBOT_TOKEN`, это пароль нашего локального сервера.

По умолчанию работает `GROKBOT_MODE=agent`: сессия читается из `%APPDATA%\Grok Bot`
под тем же пользователем Windows, DPAPI расшифровывает токен только в памяти.
Действующая сессия нужна; её обновление пока выполняет официальное приложение.
На каждый запрос создаётся отдельный временный Temporal-агент. Личные чаты не используются.

## Работа с проектом на диске

CLI самостоятельно запускает временный защищённый HTTP-сервер и выполняет цикл
OpenAI function calling. Отдельно запускать `npm start` не обязательно.

Только анализ и подготовка изменений:

```powershell
node project.mjs --root 'D:\my-project' --prompt 'Проанализируй проект, найди и исправь причину ошибки ...'
```

С записью подготовленных изменений и запуском указанной вами проверки:

```powershell
node project.mjs --root 'D:\my-project' --prompt 'Исправь ...' --apply --test 'npm test'
```

Просмотреть результат можно в JSON-отчёте, путь печатается в конце. Отчёт содержит
`before`, `after`, SHA-256 исходного содержимого и пояснение модели. Применить именно
эти изменения без повторного расходования лимита:

```powershell
node project.mjs --root 'D:\my-project' --apply-report '.\.grokbot-runs\<report>.json'
```

Функции: `list_files`, `read_file`, `search_text`, `replace_text`, `write_file`,
`delete_file`, `rename_file`, `create_directory`.
Чтение возвращает актуальное содержимое с учётом подготовленных изменений.
Изменения применяются только после успешного завершения диалога. Если модель
достигла лимита ходов или запрос завершился ошибкой, файлы не меняются.
Проверяется, не изменил ли пользователь исходные файлы во время работы.

- По умолчанию максимум 12 ходов; `--max-turns 1..50` задаёт другой предел.
  Каждый ход — отдельный запрос Grok Bot и расход его лимита, с повторной передачей истории.
- `--base-url http://127.0.0.1:8788/v1` использует уже запущенный сервер;
  для него берётся `GROKBOT_TOKEN` из окружения.
- Произвольный shell модели не предоставляется. `--test` запускает **ровно указанную
  вами** команду PowerShell после записи; код проекта при этом выполняется.
- Файлы UTF-8 до 200 KB, суммарные изменения до 2 MB; до 5000 путей в списке,
  поиск максимум по 500 файлам и 100 совпадениям. Бинарные файлы не читаются.
- Исключаются `.git`, `node_modules`, сборочные каталоги, `.ssh`, `.aws`, `.codex`,
  `.agents`, `.env*`, типичные имена secret/credential и ключевые файлы.
  Это список исключений, **не универсальный детектор секретов**.
- Запрещены выход из выбранной папки, ADS Windows, ссылки на файлы и hardlink.
  Новый файл можно создать в существующем каталоге или в каталоге, подготовленном
  `create_directory`. Родительский каталог сам не создаётся. Удаление и
  переименование требуют предварительного чтения; отчёт хранит `op`
  (`edit`, `create`, `delete`, `mkdir`), прежнее содержимое и SHA-256.
  Старый отчёт без `op` по-прежнему применяется как запись файла.
- Перед записью сохраняется отчёт с исходным содержимым в `.grokbot-runs`.
  В режиме просмотра печатается unified diff. Если запись обрывается, уже
  изменённые файлы этого запуска откатываются к содержимому из отчёта.
  Откат сам может не завершиться при сбое диска: сообщение называет и
  восстановленные, и оставшиеся изменёнными пути.
  Отчёты содержат исходники проекта; не публикуйте их без проверки.
- Файлы, которые модель читает, передаются сервису Grok Bot как текст результатов
  функций. Папка целиком не загружается и не монтируется в облачный компьютер.

## Поддержка API

| Endpoint / возможность | Состояние |
| --- | --- |
| `GET /health`, `GET /v1/capabilities` | Режим и честное описание возможностей, без запроса к модели |
| `GET /usage` | План Grok Bot, исходный `usagePercent`, доступность лимита, время сброса |
| `GET /v1/models` | `grok-bot` и явно настроенные алиасы |
| `GET /v1/models/grok-bot` | Карточка модели; неизвестная модель даёт 404 |
| `POST /v1/chat/completions` | Текстовые роли, история, функции и результаты функций, JSON/SSE |
| `tools`, `tool_choice`, `parallel_tool_calls` | Проверка имён, ID, порядка результатов, схем аргументов; функции выполняет клиент |
| `response_format` | `text`, `json_object`, `json_schema`; JSON Schema draft-07 / 2019-09 / 2020-12, проверка Ajv |
| `POST /v1/responses` | Текстовый input, instructions, функции, function_call_output, text.format, JSON/SSE |
| `previous_response_id` | Продолжение по истории в памяти сервера |
| `GET/DELETE /v1/responses/{id}` | Получение/удаление сохранённого ответа |
| `POST /v1/agent` | Прямой `{ "prompt": "..." }` через сессию desktop, с инструментами Grok Bot |

История Responses хранится максимум час, 100 записей и 16 MB на процесс; после
перезапуска пропадает. `store:false` отключает **локальное** сохранение. Это не
управляет сохранением на стороне Grok Bot. Все клиенты с одним локальным токеном
имеют общий доступ к истории: сервер рассчитан на одного владельца.
При `previous_response_id` прежние `instructions` не переносятся автоматически.

Неизвестные поля отклоняются с 400. Стандартные параметры генерации, автоматически отправляемые IDE, принимаются в режиме совместимости; неподдерживаемые перечисляются в заголовке `X-Grokbot-Ignored-Parameters` и журнале сервера. `GROKBOT_STRICT_PARAMETERS=1` возвращает строгий отказ вместо их принятия. `n=1` — единственный вариант.
Нет Images/Audio/Embeddings/Files/Batches API, remote tools, web_search, background
Responses и гарантированного выполнения любого IDE-клиента без адаптации его параметров.

### Рабочий режим agent

- Роли и функции эмулируются инструкциями в запросе Grok Bot. Собственные инструменты
  агента не отключены технически; инструкция просит их не использовать.
- Аргументы и структурированный ответ проверяются **до выдачи успешного результата**.
  Неизвестная функция, нарушение схемы или `tool_choice` дают 502 `invalid_model_output`;
  локальная функция не выполняется. Нарушение схемы аргументов не исправляется автоматически.
- Проверка результата адаптером обязательна независимо от `strict`: это **не constrained decoding**.
  Значения `strict:true` и `strict:false` принимаются с раскрытием в
  `X-Grokbot-Ignored-Parameters`; `strict:false` не отключает проверку схемы.
  Модель может нарушить схему и вызвать ошибку запроса. При
  `GROKBOT_STRICT_PARAMETERS=1` явно переданный `strict` отклоняется.
- SSE сохраняет keepalive-комментарии. Обычный текст уходит дельтами только после того,
  как следующий снимок transcript повторил этот префикс без изменений. Потоковый
  черновик, который сервис затем заменяет, клиенту не отправляется. Если уже
  подтверждённый текст всё же заменён, запрос завершается ошибкой, а не противоречивым
  ответом. Вызовы функций и JSON по-прежнему буферизуются до проверки схемы.
  `usage:null`, поскольку агент не сообщает
  достоверное число токенов. `stream_options.include_usage` принимается, но финальный
  usage-чанк появляется только при наличии измерений; числа не выдумываются.
- `temperature`, `top_p`, `stop`, `max_tokens`, `max_completion_tokens`, penalties, seed,
  reasoning_effort и verbosity в режиме agent не управляют генерацией. Они принимаются
  для совместимости с IDE с явным предупреждением; лимит ответа в токенах не гарантируется.
  Строгий режим отклоняет эти поля. В native поддерживаемые параметры передаются дальше.
- Одновременно выполняется один запрос; ещё до 4 запросов ожидают в FIFO-очереди
  не более 30 секунд. Ожидание не обращается к Grok Bot и не расходует лимит.
  При переполнении или истечении ожидания возвращается HTTP 429 `backend_busy` **до открытия SSE**,
  с `Retry-After: 1` (пауза до следующей попытки, не обещание освобождения через секунду).
  Резервирование включает исправление формата и очистку после отмены. Дедлайн 180 секунд,
  отдельного RPC 30 секунд. Отмена клиента прерывает запрос и запускает очистку.
- Ожидание взаимодействия Grok Bot даёт 409; временный агент прерывается и удаляется.
  Для продолжительных задач с подтверждениями штатного локального исполнителя используйте
  само приложение. Наш CLI обходит эту потребность за счёт собственного локального цикла,
  не меняя разрешения и политики официального исполнителя.

### Экспериментальный режим native

Добавлен прямой транспорт `aiserver.v1.InferenceService/Stream`, на основе изученного
[taowen/grokbot2api](https://github.com/taowen/grokbot2api).
Нативные сообщения и tool calls, реальный поток текстовых дельт, обновление
короткоживущего inference-токена в памяти, upstream usage при наличии.
Функции и структурированный JSON буферизуются до проверки; Responses тоже буферизован.

**Живой native-запрос для этой публикации не проверен:** обычная сохранённая desktop-сессия
не предоставляет необходимый renewal credential. Автоматическое получение такого
credential из desktop-сессии не реализовано. Для запуска нужны выданные вашему
Grok Bot внутренние реквизиты и соответствующий machine ID:

```powershell
# Секрет следует передать через окружение процесса, не записывать в исходники/историю.
$env:GROKBOT_MODE = 'native'
# GROKBOT_RENEWAL_CREDENTIAL (также SAND_INFERENCE_RENEWAL_CREDENTIAL)
# GROKBOT_MACHINE_ID (также SAND_MACHINE_ID)
npm start
```

Без них native-режим завершает запуск с явной ошибкой, не переключается на платный
API или другой аккаунт. Сам raw inference-код проверен офлайн на протокольных фикстурах.
Используется `grokBotToken` от `/sand-box/inference-credential`, для `/usage` — полученный
там же `accessToken`. Секреты и ответы авторизации не выводятся и не сохраняются на диск.
Алиас `grok-bot` выбирает upstream `grok-4.6`; настройка `GROKBOT_UPSTREAM_MODEL` задаёт
другой ID, но его доступность определяется сервисом, не адаптером.

В native-режиме передаются temperature/top_p/stop и лимит токенов. Лимит не повышается
и не игнорируется; reasoning может расходовать этот бюджет, сервис может отказать.
`developer` преобразуется в upstream system. Для известной ошибки provider 422 схема
инструмента передаётся в описании, аргументы остаются нативными tool calls и проверяются
локально. `tool_choice`/JSON Schema дополняются инструкциями и валидацией, не являются
гарантированными ограничениями генерации.

Это наиболее близкий путь к полноценному OpenAI-compatible модельному бэкенду, но
пока **экспериментальная, не подтверждённая живым запросом ветка**. Рабочая конфигурация
на вашем компьютере остаётся `agent`.

## Нужно ли держать Grok Bot открытым?

**Для нашего текстового API и локального CLI — нет**, пока действует сохранённая сессия.
Запущен должен быть Node.js сервер или `project.mjs`. Для входа/обновления сессии может
потребоваться Grok Bot. Работа зависит от действующей сессии и текущего частного протокола; при публикации этот живой сценарий повторно не проверялся.

Встроенные в сам Grok Bot локальные инструменты — другой механизм: им нужны компоненты
официального локального исполнителя. Приложение действительно поддерживает вложения
файлов и выполнение локальных операций; это подтверждено документацией
[Grok Bot Work](https://prod.cursor.com/docs/grok-bot/work) и
[Local execution](https://prod.cursor.com/docs/grok-bot/security#local-execution).
Наш CLI читает файлы сам через OpenAI-функции, поэтому эта зависимость ему не нужна.

## Настройки и эксплуатация

`GROKBOT_HOST` (127.0.0.1), `GROKBOT_PORT` (8788), `GROKBOT_TOKEN`,
`GROK_BOT_ROOT` (папка профиля Grok Bot), `GROKBOT_MODE` (agent/native).
`GROKBOT_QUEUE_LIMIT` (4, диапазон 0–32), `GROKBOT_QUEUE_WAIT_MS` (30000, максимум 120000),
`GROKBOT_MODEL_ALIASES` (список через запятую), `GROKBOT_ESTIMATE_USAGE` (0 по умолчанию).
Вне loopback обязателен токен. Browser Origin запрещён; открытого CORS нет.
Тело запроса ограничено 2 MB. Подписка и квоты не обходятся; 429 передаётся клиенту.
При сетевом сбое отправка не повторяется автоматически, чтобы не удваивать расход.

Изоляция временных агентов относится к истории диалога, а не к аккаунтным ресурсам,
памяти, подключённым сервисам и разрешениям. После аварийного завершения процесса
временный агент может остаться; при неудачной очистке выводится его ID.

## Проверки

```powershell
npm test
node scripts/smoke.mjs --live
node scripts/smoke-tools.mjs --live
```

Офлайн-набор включает отмену, квоты, framing, изоляцию, авторизацию,

Живые проверки расходуют небольшой лимит Grok Bot: вызов функции → результат функции,

проверка повторена успешно. Это практический пример ограничений эмуляции.

## Вердикт об исходном решении и заимствования

Идея использования сессии рабочая, но исходный адаптер смешивал запросы с личным агентом,
неверно сопоставлял client messageId и серверный requestId, мог возвращать чужой или
незавершённый ответ и молча игнорировал параметры OpenAI. Сейчас корреляция идёт через
`clientNonce → requestId`, завершение проверяется по transcript и состоянию idle,
каждый запрос получает свой агент с очисткой, а совместимость объявляется явно.

Кроме grokbot2api изучены [grokbot-headless](https://github.com/andreanjos/grokbot-headless)
(официальный локальный daemon под Linux) и [grokbot-sdk](https://github.com/adam91holt/grokbot-sdk)
(управление агентами через gateway). Они не дают автоматически полноценный raw OpenAI API
через Windows desktop-сессию. Использованные идеи и MIT-лицензия указаны в
[THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).


## Roo Code и Cline

Выберите **OpenAI Compatible**, а не OpenAI Native / Responses / Azure.
Base URL `http://127.0.0.1:8788/v1`, Model ID `grok-bot`, API key — локальный
`GROKBOT_TOKEN` (если сервер запущен без него, можно указать `local`).
Включите streaming и поддержку function calling. Отключите изображения и prompt caching.
Если доступны настройки ограничения токенов, лучше не включать их: agent-режим
не способен обеспечить точный токенный бюджет.

После обновления кода требуется **перезапуск процесса сервера**. Проверка версии:

```powershell
Invoke-RestMethod http://127.0.0.1:8788/health
```

Должно быть `version: 0.3.7`, `mode: agent`. Ответ старого health с текущей квотой
вместо версии означает, что продолжает работать исходный процесс.

В 0.3.1 исправлен отказ на автоматически отправляемые Roo/Cline temperature и max_tokens.
Тесты `test/ide-clients.test.mjs` используют OpenAI JS SDK 7.x и `@ai-sdk/openai-compatible` 3.x (интерфейсы `@ai-sdk/provider` 4.x):
разбор SSE, функции и второй ход после результата функции. Это тесты транспорта клиентов,
не автоматизация интерфейсов расширений.

Для живой проверки работающего сервера (Node >=22, расходует лимит):

```powershell
node scripts/smoke-ide.mjs --live
```


В 0.3.2 поддержаны отдельные валидаторы JSON Schema draft-07, 2019-09 и 2020-12:
новые ключевые слова не удаляются и не подменяются старой версией схемы. Локальные
`$defs`/`$ref` разрешены, внешние схемы не скачиваются. Текстовые части с
`cache_control: {type: "ephemeral"}` принимаются с предупреждением об отсутствии
управляемого кеширования. Реальные изображения по-прежнему отклоняются с точным
индексом сообщения/части. Старые вложения остаются в истории даже после отключения
настройки images — в таком случае начните новый текстовый чат.

`GET /v1/diagnostics` показывает последние 10 ошибок валидации с индексом поля,
без сохранения тел запросов, исходников и вложений. Применяются обычные авторизация
и запрет браузерного Origin.


В 0.3.3 при `tool_choice=auto/none` обычное текстовое объяснение принимается и при
наличии tools. Один JSON-блок функции с текстовым предисловием также поддерживается;
неоднозначные/непроверенные вызовы не исполняются. Напоминание о формате повторяется
после истории, чтобы большой результат чтения файлов не вытеснял требования транспорта.

Если ответ похож на повреждённый протокол вызова, допускается **одна дополнительная
попытка исправить формат** (до 45 секунд, дополнительный расход лимита Grok Bot).
В неё передаются только полученный ответ и схемы функций, без повторной отправки
исходного задания/истории файлов. Готовые аргументы снова проверяются. Ошибки сети,
квоты и нарушения схем аргументов не запускают эту попытку. Обычный текст не требует
дополнительного запроса. Это повышает устойчивость эмуляции, но не гарантирует
безошибочный tool calling на любой задаче.

`node scripts/smoke-files.mjs --live` проверяет чтение трёх файлов и следующий ответ
с объяснением программы через OpenAI SDK на работающем сервере.


На тесте объяснения трёх файлов воспроизведена конкретная ошибка: ответ содержал
`attempt_completion` и корректный текст, но переносы строк внутри JSON-строки были
неэкранированными. Парсер теперь локально экранирует только управляющие символы
внутри строк; имена, аргументы, кавычки и скобки не угадываются. Эта нормализация
сохраняет исходный многострочный текст, не требует повторной генерации и проходит
обычную проверку схемы. Проверены оба фактических ответа, ранее завершавшихся ошибкой.

В 0.3.4 добавлены получение конкретной модели, `x-request-id` во всех HTTP-ответах,
корректные типы ошибок 4xx и `logprobs:null` в Chat choices. Исправлено поле `type`
в ошибке Responses SSE; OpenAI SDK теперь распознаёт событие ошибки.

Chat принимает `logprobs`, `top_logprobs`, `user`, `service_tier`, `store`, `metadata`,
`logit_bias` с проверкой типов и явным перечислением в `X-Grokbot-Ignored-Parameters`.
Эти поля не управляют генерацией, тарифом или сохранением у Grok Bot; Chat-ответы
локально не сохраняются. Политика Responses `store`/`metadata` по-прежнему реализована.
Responses также принимает `user`, `service_tier`, `reasoning.effort`, `text.verbosity`
с раскрытием ограничений под исходными именами полей. Допустимы явные значения по
умолчанию `background:false`, `truncation:"disabled"`, `include:[]`. Настоящие фоновые
задания, автоматическое усечение, дополнительные включения и `max_tool_calls` пока
отклоняются. Неизвестный расход токенов и лимиты сервиса не подменяются нулями или
выдуманными rate-limit заголовками. `Retry-After` описывает только локальную занятость,
а не время сброса подписки Grok Bot.

## Изменения 0.3.5: очередь, алиасы и завершение

Очередь распространяется на agent-запросы Chat, Responses и `/v1/agent` вместе.
Она сохраняет порядок поступления; отключённый клиент удаляется из очереди.
Активный ход удерживает место до завершения исправления формата и очистки агента.
Значение `GROKBOT_QUEUE_LIMIT=0` возвращает прежний немедленный 429.
`/health` и `/v1/capabilities` показывают количество активных и ожидающих запросов.
Очередь находится в памяти одного процесса, не переживает перезапуск и не увеличивает
лимит подписки. Если основной запрос длится дольше срока ожидания, вспомогательный
запрос всё равно получит 429; бесконечного ожидания нет.

Алиасы задаются перед запуском сервера, например:

```powershell
$env:GROKBOT_MODEL_ALIASES = 'ide-model,gpt-4o'
npm start
```

Они появляются в списке моделей и работают в Chat/Responses, включая SSE и историю.
Поле `model` сохраняет выбранный алиас; `owned_by` и `X-Grokbot-Backend` указывают
на Grok Bot. Никакого переключения на настоящую GPT-4o или другую модель не происходит.
По умолчанию посторонние имена не принимаются. Алиас не добавляет изображения,
embeddings, новое контекстное окно или другие возможности, которые IDE может связать
с этим именем. Настройки возможностей клиента нужно проверять отдельно.

Опционально `$env:GROKBOT_ESTIMATE_USAGE = '1'` включает приблизительные целочисленные
значения `usage` в agent Chat/Responses, включая запрошенный финальный SSE usage-чанк.
Используется длина подготовленного prompt и сериализованного ответа, делённая на 4,
с округлением вверх. Это грубая оценка, особенно для русского текста и кода: она
не знает токенизатор Grok, скрытый контекст, reasoning, внутренние действия или расход
дополнительного исправления формата. Она не измеряет реальное контекстное окно,
стоимость или подписочный лимит. Заголовок `X-Grokbot-Usage-Source` и дополнительное
поле `grokbot_usage_source` явно помечают оценку; эта пометка сохраняется в истории.
По умолчанию остаётся `usage:null`. Native usage не заменяется эвристикой; `/usage`
по-прежнему получает фактический статус подписки от сервиса.

При штатных SIGINT/Ctrl+C и SIGTERM сервер прекращает приём запросов, отменяет очередь
и активные запросы, затем до 12 секунд ожидает завершения очистки временных агентов.
CLI обрабатывает оба сигнала, прекращает цикл работы и ожидает очистку своего сервера.
При превышении срока сервер предупреждает о возможном оставшемся агенте.
Принудительное завершение через Task Manager, `Stop-Process`, SIGKILL, сбой процесса
или выключение компьютера не гарантируют вызов обработчиков — для них гарантий очистки нет.

## Изменения 0.3.6: дельты transcript, файловые операции и откат

Обычный текст в режиме agent уходит в SSE, когда следующий снимок transcript
повторил префикс без замены. Черновик с `streaming: true` сам по себе не
считается текстом ответа: проверенный случай заменяет `partial` на другой текст,
и клиент этого черновика не видит. Если повторного снимка не было, подтверждение
idle по-прежнему отдаёт весь ответ одной дельтой. Функции, JSON Schema и
Responses не получают непроверенные дельты.

CLI умеет готовить удаление, переименование и создание каталога. Эти операции
входят в тот же отчёт и применяются только после сверки исходного содержимого.
Новый каталог не открывает путь наружу и не создаёт пропущенных родителей.
Если один из файлов не удаётся записать, предыдущие записи этого запуска
возвращаются к исходному содержимому. Просмотр печатает diff; отдельного
интерактивного подтверждения нет: запись по-прежнему требует `--apply` или
`--apply-report`.

По-прежнему не входят в этот адаптер: автоматическое получение native credential,
проверенные профили Linux/macOS и embeddings. Для embeddings нужен отдельный
модельный бэкенд, успешная заглушка была бы ложным API.

## Изменения 0.3.7: калибровка токенизатора, постраничное чтение и тайм-аут тестов

- Оценка использования токенов (`GROKBOT_ESTIMATE_USAGE=1`) теперь использует BPE-эвристику,
  учитывающую не-ASCII символы (кириллицу, CJK), предотвращая занижение расхода контекста на русском языке.
- В CLI `project.mjs` в инструмент `read_file` добавлены опциональные параметры `offset_line` (1-индексированный)
  и `limit_lines` для постраничного чтения. Файлы размером свыше 200 КБ (до 2 МБ) теперь можно читать порциями.
- В `replace_text` добавлен флаг `all: true` для замены повторяющихся вхождений, а сообщение об ошибке
  при неуникальном совпадении теперь подробно подсказывает, как устранить неоднозначность.
- Для команды `--test` добавлен настраиваемый тайм-аут `--test-timeout` (или `GROKBOT_TEST_TIMEOUT`, по умолчанию 120 сек)
  с корректным завершением дочернего процесса при зависании тестов.
- Уточнена эвристика `looksLikeToolProtocol`: режим `tool_choice: "none"` гарантированно отдаёт ответ как текст,
  а примеры кода с упоминанием `tool_calls` внутри markdown-блоков больше не приводят к ложным ошибкам протокола.
- URL сервиса в `transport.mjs` вынесен в настраиваемую переменную `GROKBOT_UPSTREAM_URL`.
